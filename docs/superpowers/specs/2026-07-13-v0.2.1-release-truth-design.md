# rate-limit-handoff v0.2.1 Release-Truth Design

**Date:** 2026-07-13
**Status:** Approved
**Release:** v0.2.1

## Objective

Ship a truthful v0.2.1 release that implements the multi-model continuity behavior
advertised by v0.2.0: same-model waiting, immediate cross-model handoff, and a temporary
switch with a planned return. Add an explicit, provider-neutral auto-run path without
guessing provider commands or executing through a shell.

## Release Context

The public v0.2.0 tag exists, but its commit message claims behavior that is not present
in the tagged code:

- `pyproject.toml` and `rate_limit_handoff.__version__` still report `0.1.0`.
- The CLI lacks `--handoff`, `--from`, `--to`, `--return-to`, `--return-at`, and
  `--prefer`.
- The scheduler creates reminders and resume scripts but does not execute an AI command
  at the reset time.
- The v0.2.0 tag and `main` have diverged. The dirty primary checkout contains the
  hardening changes and must not be altered or discarded.

v0.2.1 repairs the implementation and release lineage. It does not publish to PyPI and
does not claim live provider-availability detection.

## Product Decisions

1. **Continuity is the product category.** Scheduling is one route; cross-model handoff
   and planned return are equally explicit routes.
2. **Auto-run is opt-in.** No command runs unless the user passes `--auto-run` with the
   required explicit command argument.
3. **Commands are provider-neutral.** The program never guesses Claude, Codex, Grok,
   Antigravity, Cursor, or Hermes invocation syntax.
4. **No parent shell.** User commands are parsed to an argument vector and executed with
   `shell=False`.
5. **Reset time is the availability proxy.** v0.2.1 runs at the user-supplied time; it
   does not query provider APIs to prove that capacity has returned.
6. **Local scheduling is best-effort.** A detached local runner survives terminal exit
   but is not represented as reboot-proof or cloud-durable.
7. **Every route writes durable context first.** `handoff.md`, a Second Brain note, and
   the handoff-chain audit log are updated before any command executes.

## CLI Contract

### Same-model wait

```bash
rate-limit-handoff --schedule \
  --model claude \
  --reset-at "16:00" \
  --summary "Continue the verified release work" \
  --auto-run \
  --command 'claude -p "Read handoff.md and continue the exact next action"'
```

Without `--auto-run`, the existing reminder/resume-artifact behavior remains. With
`--auto-run`, `--command` is required and is scheduled for the parsed reset time.

### Immediate cross-model handoff

```bash
rate-limit-handoff --handoff \
  --from claude \
  --to codex \
  --summary "Continue from the active handoff chain" \
  --auto-run \
  --command 'codex exec "Read handoff.md and continue the exact next action"'
```

The context is persisted before the destination command runs. Without `--auto-run`, the
handoff is still complete as an artifact and the CLI prints the next manual action.

### Temporary switch with planned return

```bash
rate-limit-handoff --handoff \
  --from claude \
  --to codex \
  --return-to claude \
  --return-at "16:00" \
  --summary "Use Codex now, then return for the final review" \
  --auto-run \
  --command 'codex exec "Read handoff.md and continue"' \
  --return-command 'claude -p "Read handoff.md and perform the planned return"'
```

In auto-run return mode, both `--command` and `--return-command` are required. The
destination command runs only after the return plan has been persisted; the return
command is scheduled for `--return-at`.

### Resume preference

```bash
rate-limit-handoff --resume --prefer claude
```

`--prefer` changes the generated continuation instruction and surfaces the preferred
model. It does not launch that model by itself.

## Validation Rules

The CLI exits with an argparse error when:

- `--handoff` is missing `--from`, `--to`, or a non-empty `--summary`.
- Only one of `--return-to` and `--return-at` is supplied.
- `--auto-run` is used without the commands required by the selected mode.
- `--command` or `--return-command` is supplied without `--auto-run`.
- `--prefer` is used without `--resume`.
- A command parses to an empty argument vector.

Unknown provider/model names remain allowed. The tool is model-agnostic and must not
turn its built-in registry into an artificial compatibility gate.

## Architecture

### 1. CLI orchestration

`cli.py` owns argument definition, cross-argument validation, and dispatch. It converts
command strings to argument vectors once with `shlex.split` and passes structured input
to the scheduler. It does not execute commands directly.

### 2. Continuity state

A new `continuity.py` module owns the active chain and transition history.

`HandoffState` records:

- mode: `same`, `cross`, or `return`
- source model
- current model
- summary
- status
- reset or return time when applicable
- planned return model when applicable
- preferred resume model when applicable
- created and updated timestamps

The canonical machine state is stored at
`second_brain/logs/active_handoff.json`. Each transition is appended to
`second_brain/logs/handoff_chain.jsonl`.

`handoff.md` contains one replaceable block delimited by stable comments:

```markdown
<!-- rlh:active-chain:start -->
## Active Handoff Chain
...
<!-- rlh:active-chain:end -->
```

Updating the active chain replaces that block rather than appending duplicate active
sections. Existing progress history remains intact.

### 3. Execution jobs

A new `runner.py` module owns explicit command execution. Each scheduled command is
represented by a local JSON job under `second_brain/logs/jobs/` with permissions
restricted to the current user.

Each job records:

- schema version and unique ID
- mode and target model
- workspace
- scheduled time
- command argument vector
- pending/running/succeeded/failed status
- timestamps and exit code
- optional chain transition to apply when the job fires

Job files are written atomically. Commands and environment variables are not printed to
the console or copied into Second Brain notes. Documentation warns users not to place
secrets directly in command arguments because the local job file must retain the
arguments needed for execution.

### 4. Detached scheduler

For an auto-run scheduled in the future, the scheduler starts:

```bash
python -m rate_limit_handoff.runner --wait --job /absolute/path/to/job.json
```

The child uses `start_new_session=True`, redirects output to a per-job local log, waits
until the scheduled timestamp, applies the chain transition, and calls
`subprocess.run(argv, shell=False, cwd=workspace)`. The CLI prints the job path, PID,
and the machine-uptime limitation.

Immediate cross-model execution uses the same job format and execution function with a
run time of now. This keeps security, state transitions, and result recording identical
between immediate and scheduled modes.

### 5. Existing reminder path

The current `at`/resume-script reminder path remains available when `--auto-run` is not
selected. v0.2.1 does not silently convert existing `--schedule` calls into code
execution.

## Data Flow

### Same-model wait

1. Parse reset time and validate the optional auto-run command.
2. Write the scheduled continuation and Second Brain note.
3. Set the active chain to `same / waiting`.
4. Without auto-run, create the existing reminder artifact.
5. With auto-run, create the job and detached runner.
6. When the job fires, transition the chain to `same / resumed`, execute the command,
   and record the result.

### Cross-model handoff

1. Validate source, destination, and summary.
2. Write the cross-model handoff and Second Brain note.
3. Set the active chain to `cross / handed_off`, with the destination as current.
4. If auto-run is selected, execute the explicit destination command and record the
   result.

### Planned return

1. Validate destination, return model, return time, and both commands when auto-run is
   selected.
2. Write the complete return plan and Second Brain note.
3. Set the active chain to `return / temporary`, with the destination as current.
4. Create the return job before running the immediate destination command.
5. Run the destination command when requested.
6. At return time, transition the chain to `return / returned`, set the return model as
   current, execute the return command, and record the result.

## Error Handling and Safety

- Context persistence must succeed before command execution or scheduling. Failure to
  write `handoff.md`, Second Brain state, or the job file fails closed.
- Invalid argument combinations exit before any file or process mutation.
- A missing executable produces a failed job with a clear error and non-zero exit code.
- Immediate command failures are reported and returned as a non-zero CLI exit code; the
  durable handoff remains available for manual continuation.
- Scheduled failures remain recorded in the job JSON and per-job log.
- Summaries are data only and are never interpolated into an executable command.
- No provider credentials, telemetry, or network service are introduced.

## Testing Strategy

Implementation follows red-green-refactor. Required automated coverage includes:

1. Parser exposure for every advertised flag.
2. Failure cases for every invalid argument combination.
3. Same, cross, and return active-chain rendering and replacement.
4. Second Brain note content for all three modes.
5. JSONL transition history and atomic current-state writes.
6. Command parsing and `shell=False` execution.
7. Immediate cross-model success and failure behavior.
8. Scheduled job creation without waiting in tests.
9. Return-job transition from temporary model to original model.
10. Package and runtime version consistency at `0.2.1`.
11. Regression coverage for existing scheduling, parsing, Obsidian routing, and secure
    `at` submission.

Release verification runs:

```bash
pytest
ruff check .
mypy src
python -m build
```

A clean temporary environment installs the built wheel and exercises `--version`, all
three handoff modes, active-chain state, an immediate explicit command, and a scheduled
command with a near-future timestamp.
